# LSP Workspace Pull Diagnostics

## Goal
Implement the `workspace/diagnostic` LSP feature to provide diagnostics for all files within the workspace. This complements the `textDocument/diagnostic` feature by allowing clients to request diagnostics for multiple files simultaneously.

## Background
The LSP specification (3.17+) introduced a pull-model for diagnostics. While `textDocument/diagnostic` allows a client to request diagnostics for a single document, `workspace/diagnostic` extends this to the entire workspace. This is useful for initial workspace setup or periodic full-workspace checks.

The server is already configured to announce `WorkspaceDiagnostics: true` in its capabilities. This plan focuses on implementing the request handler and related types.

## Implementation Plan

### 1. Update Server Capabilities
The server already announces its support for workspace diagnostics. No changes are needed in `server/initialize.go`.

- [x] **`server/initialize.go`**:
    - The `DiagnosticProvider` already has `WorkspaceDiagnostics: true`.

### 2. Add LSP Types
New LSP types are required to handle the request/response cycle for workspace diagnostics.

- [x] **`server/types.go`**:
    - Define `WorkspaceDiagnosticParams`: Parameters for the `workspace/diagnostic` request. It typically includes an `identifier` and a list of `previousResultIds`.
    - Define `WorkspaceDiagnosticReport`: The main response container for workspace diagnostics. It contains an array of `WorkspaceDocumentDiagnosticReport`.
    - Define `WorkspaceDocumentDiagnosticReport`: Represents diagnostics for a single document within the workspace report. It includes `uri`, `kind`, `version` (optional), `resultId` (optional), and `items` (an array of `Diagnostic`).

### 3. Implement the Request Handler
A new handler will process `workspace/diagnostic` requests.

- [x] **`server/diagnostics.go`**:
    - Create a new function `handleWorkspaceDiagnostic(s *Server, id int, msg map[string]any)`.
    - **Logic**:
        1.  Unmarshal the `WorkspaceDiagnosticParams`.
        2.  Initialize an empty `WorkspaceDiagnosticReport` struct to collect results.
        3.  Iterate through all documents that the server currently manages (`s.documents` map).
        4.  For each `uri` in `s.documents`:
            *   Call the existing `generateDiagnosticsForURI(s, uri)` helper function to get the `[]Diagnostic` for that document.
            *   Create a `WorkspaceDocumentDiagnosticReport` for this document:
                *   `URI`: The document's URI.
                *   `Kind`: `DocumentDiagnosticReportKindFull` (for now, no incremental support).
                *   `Items`: The diagnostics generated by `generateDiagnosticsForURI`.
            *   Append this `WorkspaceDocumentDiagnosticReport` to the `items` slice of the `WorkspaceDiagnosticReport`.
        5.  Send the complete `WorkspaceDiagnosticReport` back to the client as the response.

### 4. Update Server Dispatcher
The main request router needs to know about the new method.

- [x] **`server/server.go`**:
    - In the `handleRequest` method's `switch` statement, add a new case for `"workspace/diagnostic"`.
    - This case should call the new `handleWorkspaceDiagnostic` handler.

### 5. Add Integration Test
Verify the implementation with a new end-to-end test.

- [x] **`server/integration_server_test.go`**:
    - Create a new test function, `TestWorkspaceDiagnosticRequest`.
    - **Setup**: Create a temporary directory with two grammar files (e.g., `a.grammar` with an error, `b.grammar` without).
    - **Test Steps**:
        1.  Open both documents using `didOpen` notifications.
        2.  Consume any initial `textDocument/publishDiagnostics` notifications generated for both files.
        3.  Send a `workspace/diagnostic` request (with an empty `previousResultIds` for simplicity, as incremental diagnostics are not yet implemented).
        4.  Read the server's response and assert that it is a `WorkspaceDiagnosticReport`.
        5.  Verify that the `WorkspaceDiagnosticReport.Items` contains two `WorkspaceDocumentDiagnosticReport` objects, one for each file.
        6.  For the document report corresponding to `a.grammar`, assert that it contains the expected diagnostic for the syntax error.
        7.  For the document report corresponding to `b.grammar`, assert that it contains no diagnostics.
