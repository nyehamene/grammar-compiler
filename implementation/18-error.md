# Parser Error Handling for Invalid Tokens

## Goal
Update the parser to check for invalid tokens generated by the tokenizer and report them as syntax errors.

## Background
The tokenizer (`token/tokenizer.go`) has the ability to detect syntax errors within certain tokens, such as an unterminated string or regex literal. Instead of halting, it creates a token with the correct `Kind` (e.g., `String`) but marks its `State` as `Invalid`.

Currently, the parser (`ast/parser.go`) consumes these tokens without checking their state, failing to report the underlying syntax error to the user. This plan outlines the steps to make the parser aware of the token state and report these errors.

## Action Plan

### 1. Update `ast/parser.go`
The primary changes will be within the parser to inspect the `State` of consumed tokens.

### 2. Modify the `parseTerminal` Method
The `parseTerminal` method is responsible for parsing `String` and `Regex` literals.

- After consuming a token with `p.next()`, check if `tok.State == token.Invalid`.
- If the token is invalid, use `p.errorf` to report a specific error.
  - For an invalid `String` token, the message should be `"unterminated string literal"`.
  - For an invalid `Regex` token, the message should be `"unterminated regex literal"`.
- The method should still return an AST node (`StringLit` or `RegexLit`) to allow parsing to continue, but the error will now be correctly registered in the parser's error list.

### 3. Modify the `expect` Method
The `expect` method is a crucial utility for consuming tokens of a specific kind. It should also be updated to handle invalid tokens.

- After consuming a token, check its `State`.
- If the token is invalid, determine the error based on its `Kind` (e.g., `String`, `Regex`) and report it using `p.errorf`. This ensures that invalid tokens used in other contexts (like the path in an `@import` directive) are also caught.

### 4. Add Parser Tests
To verify the new functionality, new test cases should be added.

- Create a `testdata/parser/invalid_token/` directory.
- Add new test files with invalid syntax:
  - `unterminated_string.grammar`: `rule = "this string never ends;`
  - `unterminated_regex.grammar`: `rule = /this regex never ends;`
- Add a new test function, `TestParseInvalidToken`, to `ast/parser_test.go` (or create the test file if it doesn't exist).
- This test should parse the new invalid files and assert that the `parser.ParseFile()` function returns an error and that the error message contains the expected text (e.g., "unterminated string literal").
